# Executive Summary

VTK (see [repository](https://gitlab.kitware.com/vtk/vtk) and [website](https://vtk.org/)) is developing a WebGPU rendering backend to create one modern graphics path that can operate across native desktop systems and WebAssembly applications. The effort addresses an escalating maintenance problem: supporting medical and scientific rendering separately through OpenGL, browser APIs, Vulkan, Metal, and Direct3D multiplies window-system integration, shaders, resource management, testing, and defect correction. WebGPU exposes a portable modern API, while Dawn maps that API to native graphics implementations.

The central architectural change separates operating-system window ownership from graphics rendering. `vtkHardwareWindow` and its platform subclasses manage Win32, Cocoa, X11, Wayland, and WebAssembly surfaces. `vtkWebGPURenderWindow` consumes those surfaces and owns WebGPU adapters, devices, textures, buffers, pipelines, and presentation. This decoupling removes the need to build an entire WebGPU render-window stack for each platform. `QVTKWebGPUWidget` demonstrates the resulting Qt ownership model, with conditional `VTK_ENABLE_WEBGPU` integration and dedicated image-regression tests, while the same boundary supports compositor-managed Wayland windows, headless rendering, and browser canvases.

The backend has progressed from foundational polygonal rendering toward practical feature coverage. 2026 work added or strengthened 2D image rendering, all VTK light types, projection-specific skyboxes, batched polydata, 16-bit GLES3/WASM textures for medical data, resize correctness, safe VTK-WASM/WebGPU finalization, physically based rendering, and render-pass infrastructure. Alignment around `DEPTH_24_PLUS_8_STENCIL` corrected depth-buffer artifacts and premature compute-shader exits. A draft Slang prototype is exploring more maintainable shader substitution, reflection, inspection, and debugging while retaining WGSL as the target.

The portability boundary is now concrete rather than aspirational. VTK public headers use the standardized WebGPU C API exclusively, contain no Dawn-specific or implementation-specific types, and no longer require downstream consumers to use C++20. Native builds can select compatible implementations through dlopen-based proc tables. Multiple Dawn updates are still necessary internally as the upstream API evolves, but they no longer define VTK's public interface.

WebGPU's primary value to VTK is sustainability and continuity, not a claim that a portable layer will always outperform hand-tuned native APIs. Feature coverage remains backend-specific: the GLES3/WebGL WASM path supports 16-bit browser volume workflows, while the WebGPU volume mapper remained under development and its trame-vtklocal configurations were expected failures as of August 3, 2026. Native CI expanded to macOS and Windows in addition to Linux, including x86_64 and arm64, although flaky Windows jobs were later removed to preserve a reliable signal. Remaining work includes WebGPU volume and render-pass completeness, representative performance evaluation, stable cross-platform coverage, and a broader concurrency model for GPU resource access.
