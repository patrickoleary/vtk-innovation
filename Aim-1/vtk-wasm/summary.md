# Executive Summary

VTK-WASM 2.x (see vtk-wasm [website](https://kitware.github.io/vtk-wasm/)) brings compiled C++ VTK into web applications through WebAssembly. The project addresses a long-standing deployment tradeoff: server-side rendering preserves VTK's capabilities but adds infrastructure and latency, while JavaScript rewrites provide local interaction but duplicate implementation and cover only part of the toolkit. VTK-WASM (see the vtk-wasm [repository](https://github.com/Kitware/vtk-wasm)) preserves the core VTK data and pipeline model while allowing algorithms and rendering to execute inside the browser sandbox.

The current architecture separates runtime loading from scene ownership. The `@kitware/vtk-wasm` package loads and caches WebAssembly runtimes by bundle, rendering backend, and execution mode. Each runtime creates standalone sessions for JavaScript-owned pipelines or remote sessions for scenes owned by a Python/C++ server. JavaScript proxies expose wrapped VTK classes; canvas registration connects VTK render windows to framework-managed HTML elements; object serialization and binary-blob caching support remote synchronization; and explicit disposal manages browser component lifecycles.

Work in 2026 substantially matured this product layer. The JavaScript library was redesigned around `loadAsync()`, concurrent configurations, clear standalone/remote sessions, generated API documentation, CDN-ready bundles, and reliable cleanup. VTK core changes allowed browser event loops to coexist, fixed object ownership and WebGPU finalization, restored Linux WASM CI, added JSON type manifests, adopted a unified asynchronous execution path, and added signed and unsigned 16-bit textures on the GLES3/WASM path. trame-vtklocal (see [repository](https://github.com/Kitware/trame-vtklocal)) added an end-to-end configuration matrix across WebGL, WebGPU, wasm32, wasm64, synchronous/asynchronous execution, geometry updates, mount/unmount behavior, multiple views, and volume rendering.

VTK-WASM also benefits directly from the shared WebGPU modernization. The backend now includes 2D image mapping, skybox projection shaders, repeated-geometry batching, physically based shading, all VTK light types, corrected depth/stencil attachments, and safe browser-view teardown. VTK public WebGPU interfaces have moved from Dawn's C++ wrapper to the WebGPU C API, aligning the native and Emscripten integration boundary while reducing downstream toolchain coupling.

The result is a practical route for C++, JavaScript, Python, trame, and eventually broader PyVista audiences to use the same visualization foundation. Backend coverage is not yet identical: 16-bit CT and MRI volume rendering is supported through GLES3/WebGL, while the WebGPU volume mapper remained under active development and its trame-vtklocal configurations were expected failures as of the August 3, 2026 snapshot. The remaining work centers on expanding serialization and module coverage, reducing bundle and startup costs, completing WebGPU volume and render-pass coverage, improving generated type definitions, and continuously testing the contract between VTK builds and downstream browser applications.
