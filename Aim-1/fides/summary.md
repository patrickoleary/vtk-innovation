# Executive Summary

The Fides–Conduit integration provides a schema-driven, in-memory route from medical and scientific arrays to VTK data objects. It addresses the recurring cost of writing format-specific VTK readers for simulation, experimental, proprietary, and AI-generated data. Instead of combining data access, domain interpretation, and VTK object construction in one C++ reader, the workflow divides those responsibilities: an existing library opens the data, a Conduit Node represents the relevant arrays, and a Fides JSON model maps those arrays to coordinates, topology, fields, partitions, and time.

Fides (see [repository](https://fides.readthedocs.io/en/latest/?badge=latest) and [documentation](https://fides.readthedocs.io/en/latest/?badge=latest)) was originally centered on ADIOS2 data. Adding Conduit required a backend architecture that separates source access from data-model interpretation and isolates source-specific types behind registries. VTK's `vtkFidesReader` can accept a named Conduit Node along with the Fides schema, allowing memory-resident data to enter standard VTK filters and renderers. When the data layout and ownership permit, Conduit's external-array facilities can minimize copying; callers remain responsible for preserving array lifetimes.

The VTK integration began with [VTK !12641](https://gitlab.kitware.com/vtk/vtk/-/merge_requests/12641). In 2026, [VTK !13397](https://gitlab.kitware.com/vtk/vtk/-/merge_requests/13397) moved the Fides reader/writer toward a native VTK backend, reducing conversion layers and aligning the result directly with VTK's data model. Fides testing also expanded to cover deterministic structured and unstructured datasets, homogeneous and mixed cell shapes, scalar and vector fields, multiple blocks, multiple sources, embedded schemas, and file- and string-based data models.

This architecture is most valuable where formats or schemas evolve quickly, data is already present in memory, or a domain-specific reader already exists. It does not remove the need for stable community readers, nor does every Conduit mapping automatically provide zero-copy access. It provides a maintainable alternative: write and test a declarative mapping before committing to another bespoke visualization reader.
